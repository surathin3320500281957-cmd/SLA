# SLA Dashboard — README

เอกสารสรุปโครงสร้าง ข้อมูล และ logic ทั้งหมดของ `index.html` เพื่อให้แชทครั้งต่อไป (ไม่ว่าจะอัปเดตข้อมูลใหม่ หรือแก้ไขเพิ่มเติม) เข้าใจภาพรวมได้เร็วขึ้น ไม่ต้องไล่หาทีละจุดใหม่ทุกครั้ง

---

## 1. ภาพรวมไฟล์และการ mapping กับ sheet ต้นฉบับ (สำคัญมาก)

ไฟล์เดียว `index.html` — HTML + CSS + JavaScript (Chart.js) ไม่มี backend, ข้อมูลทั้งหมด**ฝังอยู่ในไฟล์เป็น JSON literal** (3 ตัวแปรหลัก: `AF`, `NA`, `MN`)

**แต่ละแท็บมีที่มาจากคนละ sheet ใน Excel ต้นฉบับ ไม่ใช่ filter จาก AF ทั้งหมด:**

| แท็บ | ตัวแปรใน JS | ที่มาจริง | ความสัมพันธ์กับ AF |
|---|---|---|---|
| 1. ภาพรวม | `AF` | Sheet **AF** | เป็น array หลัก |
| 2. ไม่ดำเนินการ(ภาพรวม) | `OVNA` | `= AF.filter(status==='ไม่ดำเนินการ')` | **derived จาก AF จริง** (บรรทัด `const OVNA=AF.filter(...)`) |
| 3. ไม่ดำเนินการ(สคล/สคจ ชี้แจง) | `NA` | Sheet **สำหรับกรอง-ตรวจสอบ** | **array แยกต่างหาก ไม่ได้ derive จาก AF** — เป็น JSON literal ของตัวเอง (`const NA=[...]`) |
| 4. ไม่ดำเนินการ(ข้อมูลหน่วยงานอื่น) | `MN` | Sheet **รายเดือน-ชน** | **array แยกต่างหาก** เช่นกัน |

⚠️ ข้อควรระวัง: เพราะ `NA` และ `MN` เป็น array แยก ไม่ผูกกับ `AF` — **การแก้ไข/เพิ่มฟิลด์ใน `AF` จะไม่ไหลไปถึง `NA`/`MN` อัตโนมัติ ต้องทำ join ด้วยรหัสลูกค้า (`cust`) แยกต่างหากเสมอ** (ดูหัวข้อ 5)

**ขนาดข้อมูล ณ ชุดล่าสุด:** AF 1,023 | OVNA/NA 163 | MN 151

## 3. ⚠️ ลักษณะพิเศษของข้อมูลดิบที่ "ต้องรู้ไว้ก่อนแก้อะไร"

ข้อมูลจากระบบต้นทางมี pattern ที่ทำให้ตารางรายละเอียด**ดูขัดแย้งกันเอง**ถ้าไม่ระวัง (ไม่ใช่บั๊ก แต่เป็นลักษณะข้อมูลจริง) — พบทั้งหมด 2 จุด ทั้งคู่มี pattern เดียวกันคือ **"ล้ำหน้าไม่เกิน 1 ขั้นเสมอ"**:

### 3.1 คอลัมน์วันที่ d01-d11
ตั้งแต่สถานะ "รอการจัดจ้าง" (stage 7) เป็นต้นไป **คอลัมน์วันที่ของสถานะถัดไป (stage+1) จะมีวันที่ติดมาด้วยเสมอ 1 คอลัมน์** แม้ `update` ยังไม่ขยับไปถึงสถานะนั้นจริง — ยืนยันด้วยข้อมูลจริงว่า**ไม่เคยเกิน 1 คอลัมน์ล่วงหน้า**

### 3.2 ฟิลด์ `ck_custcare_st_grp` ("เช็คสถานะซ่อมหลังสุด")
เมื่อ `update` อยู่ใน 11 สถานะ (กำลังซ่อมอยู่) ค่า `ck_custcare_st_grp` จะ**ตรงกับ `update` พอดี หรือล้ำหน้าไป 1 สถานะเท่านั้น** (diff=0 → 354, diff=+1 → 344, diff=-1 → 16 เฉพาะกรณี "ขอเบิกเงินค่าจ้าง" ซึ่งไม่ถือว่าผิดปกติ)

ทั้ง 2 จุดนี้แก้ไปแล้วด้วย logic ในหัวข้อ 4 (`dCell`, `ckStatus`) — **เฉพาะแท็บ Overview เท่านั้น** แท็บอื่นไม่ต้องแก้เพราะไม่เจอ case นี้เลย (ดูหัวข้อ 4.2)

## 4. Logic / ฟังก์ชันหลักที่แก้ไว้แล้ว (ห้ามลบ/แก้โดยไม่เข้าใจก่อน)

ทั้งหมดอยู่ในส่วน `<script>` ประมาณบรรทัด 454-470

| ฟังก์ชัน/ค่าคงที่ | หน้าที่ |
|---|---|
| `STAGES11` | ลำดับ 11 สถานะมาตรฐาน (ห้ามสลับลำดับ ใช้คู่กับ d01-d11) |
| `STAGES12` | STAGES11 + "ไม่ดำเนินการ" |
| `curStage(x)` | คืนค่า `x.update` ถ้าอยู่ใน STAGES11, ไม่งั้นคืน `'ไม่ดำเนินการ'` — **ใช้แทน `x.update` ทุกที่ที่เกี่ยวกับ filter/กราฟ/pivot ของ "สถานะซ่อมปัจจุบัน"** |
| `stageIdx(x)` | คืนลำดับ (1-11) ของสถานะปัจจุบัน, คืน `0` ถ้าอยู่นอก STAGES11 |
| `dCell(x,n)` | คืนค่า `d0n` เฉพาะถ้า `n <= stageIdx(x)` ไม่งั้นคืน `'—'` — **ใช้แทนการอ่าน `x.d01..x.d11` ตรงๆ ในตาราง Overview เท่านั้น** (แก้ปัญหาข้อ 3.1) |
| `ckStatus(x)` | ถ้า `update` อยู่ใน STAGES11 → คืน `x.update` (sync ให้ตรงเป๊ะ); ถ้าไม่ → คืน `x.ck_custcare_st_grp` ตามเดิม — **ใช้แทนการอ่าน `x.ck_custcare_st` / `x.ck_custcare_st_grp` ตรงๆ ในตาราง+filter Overview** (แก้ปัญหาข้อ 3.2) |
| `UPD_REF_DATE` | วันที่อ้างอิงคำนวณ "วันค้างสถานะซ่อมหลังสุด" — **ต้องอัปเดตทุกครั้งที่ข้อมูลใหม่** ให้ตรงกับวันที่ในข้อความ "อัปเดต: ..." ที่ header บนสุดของ dashboard |

### 4.1 สิ่งที่ถูกลบออกไปแล้ว (อย่าเอากลับมา)
- Dropdown filter "สถานะซ่อมถัดไป" (`ov-next`) — ถูกลบออกจาก DOM, `ovClear()`, และ `initDDs()` ทั้งหมดแล้ว เพราะไม่เคยถูกใช้กรองจริง (dead code) ฟิลด์ `next_custcare` ในข้อมูลดิบยังอยู่เฉยๆ ไม่ต้องไปยุ่ง

### 4.2 ทำไม `dCell`/`ckStatus` แก้แค่แท็บ Overview
ตรวจสอบแล้วว่าทุก record ในแท็บ OVNA/NA/MN มี `update` อยู่นอก STAGES11 เสมอ (เป็น "ไม่ดำเนินการ" โดยธรรมชาติของชุดข้อมูล) ดังนั้นเงื่อนไข `STAGES11.includes(x.update)` จะเป็น `false` เสมอสำหรับ 3 แท็บนี้ — การเอา `dCell`/`ckStatus` ไปใช้ก็จะได้ผลเหมือนเดิมทุกประการ (no-op) จึงไม่จำเป็นต้องแก้

### 4.3 เรื่อง `<ปรับสรุปการUPDATE>` — ไม่ต้องทำ logic lookup ใน JS
`<ปรับสรุปการUPDATE>` ใน sheet "สำหรับกรอง-ตรวจสอบ" และ "รายเดือน-ชน" เป็น**ผลลัพธ์ที่ทีมงานทำสูตร VLOOKUP เทียบกับ AF ไว้ในไฟล์ Excel เรียบร้อยแล้วก่อนส่งออกมา** ดังนั้นค่าที่อ่านได้จากคอลัมน์นี้คือค่าล่าสุดที่ถูกต้องอยู่แล้วทุกครั้ง — **dashboard ไม่ต้องเขียน logic lookup/verify กับ AF ซ้ำใน JS** อ่านมาใช้เป็น `update` ตรงๆ ได้เลย (ตรวจสอบแล้ว 100% match ทั้ง NA และ MN)

## 5. รหัสลูกค้า + ประเภทสัญญา (เพิ่มล่าสุด)

เพิ่ม 2 คอลัมน์ใน**ตารางรายละเอียดทุกแท็บ** ต่อจาก "บ้านเลขที่":

| คอลัมน์ | ฟิลด์ | ที่มา |
|---|---|---|
| รหัสลูกค้า | `cust` (ใช้ค่าเดิมที่มีอยู่แล้ว) | ตรงกับ `CUST_CODE`/`รหัสลูกค้า` ทุก sheet 100% |
| ประเภทสัญญา | `contract_type` (ฟิลด์ใหม่) | `CONTRACT_TYPE1` **มีอยู่เฉพาะใน sheet AF เท่านั้น** |

เพราะ `CONTRACT_TYPE1` มีแค่ใน AF sheet เดียว การเติมฟิลด์ `contract_type` ให้ `NA` และ `MN` (ซึ่งเป็น array แยก ไม่ผูกกับ AF ตามหัวข้อ 1) **ต้อง join ย้อนกลับด้วยรหัสลูกค้า (`cust`) ทุกครั้งที่อัปเดตข้อมูลใหม่**:

```python
ct_map = {str(cust_code): contract_type1 for แต่ละแถวใน AF sheet}
for r in AF: r['contract_type'] = ct_map.get(str(r['cust']), '')
for r in NA: r['contract_type'] = ct_map.get(str(r['cust']), '')
for r in MN: r['contract_type'] = ct_map.get(str(r['cust']), '')
```

**อัตรา join สำเร็จ ณ ชุดข้อมูลล่าสุด:** AF 1023/1023, NA 163/163, MN 138/151

**13 รายการใน MN ที่ join ไม่เจอ** = ลูกค้าที่ **"ส่งมอบแล้ว"** (ยืนยันแล้ว 100% ว่าเป็นเหตุผลเดียว) ซึ่งหมายความว่างานจบแล้ว เลยไม่มีอยู่ใน sheet AF อีกต่อไป — เป็นเรื่องปกติ **ไม่ใช่ error** ให้แสดง "—" สำหรับกรณีนี้ (โค้ดจัดการให้อัตโนมัติแล้วผ่าน `x.contract_type||'—'`)

## 6. จุดที่ต้อง sync กันเสมอเวลาแก้ไขเพิ่ม (เฉพาะแท็บ Overview)

ถ้าจะเพิ่ม/แก้อะไรเกี่ยวกับ "สถานะซ่อมปัจจุบัน" หรือ "เช็คสถานะซ่อมหลังสุด" ในแท็บ **ภาพรวม (Overview)** ต้องแก้ให้ครบทุกจุดพร้อมกัน ไม่งั้นตัวเลขจะไม่ตรงกัน:

**สถานะซ่อมปัจจุบัน (curStage):**
1. Dropdown `ov-cur` → populate ด้วย `STAGES12`
2. `ovFiltered()` → match ด้วย `curStage(x)===cur`
3. กราฟวงกลม `CH.st` (init + re-render ใน `renOv()`) → ใช้ `STAGES12` + `curStage(r)`
4. Pivot table (`renOv()` ส่วนท้าย) → ใช้ `STAGES12` + `curStage(r)` ทั้ง 3 แถว (รายบริษัท/รวมต่อกอง/รวมทั้งหมด)
5. ตาราง Pivot **ต้องเช็คว่าผลรวม 12 คอลัมน์ = ยอดรวมเสมอ**

**เช็คสถานะซ่อมหลังสุด (ckStatus):**
1. Dropdown `ov-ck` → populate ด้วย `[...new Set(AF.map(ckStatus).filter(Boolean))].sort()`
2. `ovFiltered()` → match ด้วย `ckStatus(x)===ck`
3. คอลัมน์ในตารางรายละเอียด → แสดง `ckStatus(x)` (ไม่ใช่ `x.ck_custcare_st` ตรงๆ)
4. **`ckLagValue()` / คอลัมน์ "วันค้างสถานะซ่อมหลังสุด" ไม่ต้องแตะ** — อ่านจาก `x.ck_custcare_st` (raw) แยกต่างหาก ไม่ขัดแย้งกับข้อความที่ sync แล้ว

## 7. Workflow การอัปเดตข้อมูล (Excel → Dashboard)

ผู้ใช้จะส่งไฟล์ Excel มาเป็นระยะ **โครงสร้างคอลัมน์เหมือนต้นฉบับทุกอย่าง** ขั้นตอนตอนอัปเดต:

1. อ่านไฟล์ Excel (ใช้ xlsx skill) ทั้ง 3 sheet ที่เกี่ยวข้อง: **AF** (header แถวที่ 3, index=2), **สำหรับกรอง-ตรวจสอบ** (header แถวที่ 3, index=2), **รายเดือน-ชน** (header แถวที่ 61, index=60 — ตำแหน่งอาจขยับได้ ให้ค้นหาแถวที่มีคำว่า "รหัสลูกค้า"/"ปรับสรุปการUPDATE" ก่อนเสมอ)
2. แมปคอลัมน์ตามหัวข้อ 2 แล้วแทนที่ข้อมูลใน `AF`, `NA`, `MN` ด้วยชุดใหม่ทั้งหมด
3. **ทำ join `contract_type` ใหม่ทุกครั้ง** ตามหัวข้อ 5 (ห้ามลืม เพราะ NA/MN เป็น array แยก ไม่ inherit จาก AF อัตโนมัติ)
4. **อัปเดตวันที่ 2 จุด:**
   - Header บนสุด: `"อัปเดต: DD-MM-YYYY(พ.ศ.) HH:MM น."`
   - `const UPD_REF_DATE=new Date(YYYY,M-1,D);` (เดือนใน JS Date เริ่มที่ 0)
5. **ห้ามแก้/ลบ** ฟังก์ชันในหัวข้อ 4 โดยไม่จำเป็น — โค้ด logic ควรทำงานได้ทันทีกับข้อมูลชุดใหม่ตราบใดที่โครงสร้างคอลัมน์เหมือนเดิม
6. ตรวจสอบก่อนส่งกลับทุกครั้ง:
   - JS syntax (`node -e "new Function(...)"` หรือเทียบเท่า)
   - จำลอง filter สำคัญด้วย Python/Node เทียบกับข้อมูลจริงชุดใหม่ (เช่น เช็คว่า pivot รวมคอลัมน์ = ยอดรวม, เช็คว่า curStage/ckStatus ยัง sync ถูกต้อง, เช็คอัตราการ join contract_type)
   - นับ `<th>` vs `<td>` ต่อแถวในแต่ละตารางให้ตรงกัน (ระวัง cell ที่สร้างผ่านฟังก์ชัน เช่น `ckLagTd()` จะไม่นับด้วย regex ธรรมดา ต้องดูโค้ดจริงประกอบ)

## 8. ประวัติการแก้ไข (สรุปสั้นๆ เรียงตามลำดับ)

1. ลบ filter "สถานะซ่อมถัดไป" (ov-next) ออกจากระบบทั้งหมด (เป็น dead code)
2. เพิ่ม "ไม่ดำเนินการ" เป็นตัวเลือกที่ 12 ใน filter สถานะซ่อมปัจจุบัน (`curStage`, `STAGES12`)
