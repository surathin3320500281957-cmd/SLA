# SLA Dashboard — README

เอกสารสรุปโครงสร้าง ข้อมูล และ logic ทั้งหมดของ `index.html` เพื่อให้แชทครั้งต่อไป (ไม่ว่าจะอัปเดตข้อมูลใหม่ หรือแก้ไขเพิ่มเติม) เข้าใจภาพรวมได้เร็วขึ้น ไม่ต้องไล่หาทีละจุดใหม่ทุกครั้ง

---

## 1. ภาพรวมไฟล์

ไฟล์เดียว `index.html` — HTML + CSS + JavaScript (Chart.js) ไม่มี backend, ข้อมูลทั้งหมด**ฝังอยู่ในไฟล์เป็น JSON literal**:

| ตัวแปร | บรรทัดประมาณ | ใช้ในแท็บ | เนื้อหา |
|---|---|---|---|
| `AF` | ~414 | ภาพรวม (Overview), ไม่ดำเนินการ (OVNA/NA) | ข้อมูลหลักทั้งหมด (1,023 รายการ ณ ชุดข้อมูลล่าสุด) |
| `MN` | ~704 (ประมาณ, ค้นด้วย `const MN=`) | รอลงระบบ SLA | ชุดข้อมูลแยกต่างหาก (151 รายการ ณ ชุดข้อมูลล่าสุด) |

**แท็บทั้งหมดในระบบ:**
1. **ภาพรวม** (`tp-ov`) — ใช้ `AF` ทั้งชุด, ฟังก์ชันหลัก `renOv()` / `ovFiltered()`
2. **ไม่ดำเนินการภาพรวม** (`tp-ovna`) — ใช้ `OVNA = AF.filter(status==='ไม่ดำเนินการ')`, ฟังก์ชัน `renOvNA()` / `ovnaFiltered()` (ผ่าน `ovnaBase()`)
3. **ไม่ดำเนินการ(สาขา)** (`tp-na`) — ใช้ `NA` (จาก `naBase()`), คล้าย OVNA
4. **รอลงระบบ SLA** (`tp-mn`) — ใช้ `MN`, ฟังก์ชัน `renMn()`

## 2. โครงสร้างฟิลด์สำคัญใน `AF` (record หนึ่งแถว)

```
dept, bp, proj, house, cust, cust_name, change_status,
status,          // สถานะรวม เช่น "ซ่อม" / "ไม่ดำเนินการ"
update,          // "สถานะซ่อมปัจจุบัน" — ค่าจริงที่ควรอิงเป็นหลัก
guarantee, confirm_flag,
next_custcare,   // ⚠️ เลิกใช้แล้ว (ดูหัวข้อ 4.1) ยังมีอยู่ในข้อมูลดิบเฉยๆ ไม่ผูกกับระบบใดๆ
start_con, due_last, due_amt, overdue, debt, days_lag,
ck_custcare_st,      // ข้อความดิบ อาจมีวันที่ 8 หลักนำหน้า เช่น "20260806 ดำเนินการซ่อม"
ck_custcare_st_grp,  // = ck_custcare_st ตัดวันที่ออก, หรือ "ไม่เคยซ่อม" ถ้าว่าง
d01..d11,        // วันที่ของแต่ละสถานะใน STAGES11 ตามลำดับ (d01=รับคำร้องแจ้งซ่อม ... d11=ขอเบิกเงินค่าจ้าง)
aging09, ck_aging09
```

### STAGES11 (ลำดับสถานะซ่อมมาตรฐาน 11 ขั้น — ต้องเรียงลำดับนี้เสมอ)
```
1. รับคำร้องแจ้งซ่อม
2. สำรวจซ่อม
3. ยืนยันการสำรวจซ่อม
4. ประมาณราคา
5. ตรวจสอบและรับรองราคา
6. อนุมัติสรุปค่าก่อสร้าง
7. รอการจัดจ้าง
8. จัดหาผู้รับจ้าง
9. ดำเนินการซ่อม
10. ดำเนินการเสร็จสิ้น
11. ขอเบิกเงินค่าจ้าง
```
`d01` ตรงกับสถานะที่ 1, `d02` ตรงกับสถานะที่ 2, ... `d11` ตรงกับสถานะที่ 11 (1:1 เสมอ)

`STAGES12 = [...STAGES11, 'ไม่ดำเนินการ']` — ใช้เมื่อไหร่ก็ตามที่ต้องรวม "ไม่ดำเนินการ" เป็นตัวเลือกที่ 12

## 3. ⚠️ ลักษณะพิเศษของข้อมูลดิบที่ "ต้องรู้ไว้ก่อนแก้อะไร"

ข้อมูลจากระบบต้นทางมี pattern ที่ทำให้ตารางรายละเอียด**ดูขัดแย้งกันเอง**ถ้าไม่ระวัง (ไม่ใช่บั๊ก แต่เป็นลักษณะข้อมูลจริง):

### 3.1 คอลัมน์วันที่ d01-d11
ตั้งแต่สถานะ "รอการจัดจ้าง" (stage 7) เป็นต้นไป **คอลัมน์วันที่ของสถานะถัดไป (stage+1) จะมีวันที่ติดมาด้วยเสมอ 1 คอลัมน์** แม้ `update` ยังไม่ขยับไปถึงสถานะนั้นจริง เช่น `update="รอการจัดจ้าง"` (d07 มีวันที่) แต่ `d08` (จัดหาผู้รับจ้าง) ก็มีวันที่เดียวกันติดมาด้วย — ยืนยันด้วยข้อมูลจริงว่า**ไม่เคยเกิน 1 คอลัมน์ล่วงหน้า**

### 3.2 ฟิลด์ `ck_custcare_st_grp` ("เช็คสถานะซ่อมหลังสุด")
เมื่อ `update` อยู่ใน 11 สถานะ (กำลังซ่อมอยู่) ค่า `ck_custcare_st_grp` จะ**ตรงกับ `update` พอดี หรือล้ำหน้าไป 1 สถานะเท่านั้น** (ไม่เคยล้ำเกิน 1, ยืนยันด้วยข้อมูลจริง 714 รายการ: diff=0 → 354, diff=+1 → 344, diff=-1 → 16 เฉพาะกรณี "ขอเบิกเงินค่าจ้าง")

## 4. Logic / ฟังก์ชันหลักที่แก้ไว้แล้ว (ห้ามลบ/แก้โดยไม่เข้าใจก่อน)

ทั้งหมดอยู่ในส่วน `<script>` ประมาณบรรทัด 450-470

| ฟังก์ชัน/ค่าคงที่ | หน้าที่ |
|---|---|
| `STAGES11` | ลำดับ 11 สถานะมาตรฐาน (ห้ามสลับลำดับ ใช้คู่กับ d01-d11) |
| `STAGES12` | STAGES11 + "ไม่ดำเนินการ" |
| `curStage(x)` | คืนค่า `x.update` ถ้าอยู่ใน STAGES11, ไม่งั้นคืน `'ไม่ดำเนินการ'` — **ใช้แทน `x.update` ทุกที่ที่เกี่ยวกับ filter/กราฟ/pivot ของ "สถานะซ่อมปัจจุบัน"** |
| `stageIdx(x)` | คืนลำดับ (1-11) ของสถานะปัจจุบัน, คืน `0` ถ้าอยู่นอก STAGES11 |
| `dCell(x,n)` | คืนค่า `d0n` เฉพาะถ้า `n <= stageIdx(x)` ไม่งั้นคืน `'—'` — **ใช้แทนการอ่าน `x.d01..x.d11` ตรงๆ ในตาราง Overview เท่านั้น** (แก้ปัญหาข้อ 3.1) |
| `ckStatus(x)` | ถ้า `update` อยู่ใน STAGES11 → คืน `x.update` (sync ให้ตรงเป๊ะ); ถ้าไม่ → คืน `x.ck_custcare_st_grp` ตามเดิม — **ใช้แทนการอ่าน `x.ck_custcare_st` / `x.ck_custcare_st_grp` ตรงๆ ในตาราง+filter Overview** (แก้ปัญหาข้อ 3.2) |
| `UPD_REF_DATE` | วันที่อ้างอิงคำนวณ "วันค้างสถานะซ่อมหลังสุด" — **ต้องอัปเดตทุกครั้งที่ข้อมูลใหม่** ให้ตรงกับวันที่ในข้อความ "อัปเดต: ..." ที่ header บนสุดของ dashboard |

### 4.1 สิ่งที่ถูกลบออกไปแล้ว (อย่าเอากลับมา)
- Dropdown filter "สถานะซ่อมถัดไป" (`ov-next`) — ถูกลบออกจาก DOM, `ovClear()`, และ `initDDs()` ทั้งหมดแล้ว เพราะไม่เคยถูกใช้กรองจริง (dead code) ฟิลด์ `next_custcare` ในข้อมูลดิบยังอยู่เฉยๆ ไม่ต้องไปยุ่ง

## 5. จุดที่ต้อง sync กันเสมอเวลาแก้ไขเพิ่ม

ถ้าจะเพิ่ม/แก้อะไรเกี่ยวกับ "สถานะซ่อมปัจจุบัน" หรือ "เช็คสถานะซ่อมหลังสุด" ในแท็บ **ภาพรวม (Overview)** ต้องแก้ให้ครบทุกจุดพร้อมกัน ไม่งั้นตัวเลขจะไม่ตรงกัน:

**สถานะซ่อมปัจจุบัน (curStage):**
1. Dropdown `ov-cur` → populate ด้วย `STAGES12`
2. `ovFiltered()` → match ด้วย `curStage(x)===cur`
3. กราฟวงกลม `CH.st` (init + re-render ใน `renOv()`) → ใช้ `STAGES12` + `curStage(r)`
4. Pivot table (`renOv()` ส่วนท้าย) → ใช้ `STAGES12` + `curStage(r)` ทั้ง 3 แถว (รายบริษัท/รวมต่อกอง/รวมทั้งหมด)
5. ตาราง Pivot **ต้องเช็คว่าผลรวม 12 คอลัมน์ = ยอดรวมเสมอ**

**เช็คสถานะซ่อมหลังสุด (ckStatus):**
1. Dropdown `ov-ck` → populate ด้วย `[...new Set(AF.map(ckStatus).filter(Boolean))].sort()`
2. `ovFiltered()` → match ด้วย `ckStatus(x)===ck`
3. คอลัมน์ในตารางรายละเอียด → แสดง `ckStatus(x)` (ไม่ใช่ `x.ck_custcare_st` ตรงๆ)
4. **`ckLagValue()` / คอลัมน์ "วันค้างสถานะซ่อมหลังสุด" ไม่ต้องแตะ** — อ่านจาก `x.ck_custcare_st` (raw) แยกต่างหาก ไม่ขัดแย้งกับข้อความที่ sync แล้ว เพราะ record กลุ่มที่ sync (diff 0/±1) ไม่เคยมีวันที่ฝังมาอยู่แล้ว

### ⚠️ สำคัญ: การแก้ทั้งหมดข้างบนนี้ทำเฉพาะแท็บ "ภาพรวม" (`ovBody`, `pvWrap`) เท่านั้น
แท็บ ไม่ดำเนินการ (OVNA/NA) และ รอลงระบบ SLA (MN) **ไม่ได้แก้และไม่จำเป็นต้องแก้** เพราะข้อมูลในแท็บเหล่านี้ทุก record มี `update` อยู่นอก STAGES11 เสมอ (ยืนยันด้วยข้อมูลจริง: OVNA/NA 163 รายการ = 0 ที่อยู่ใน STAGES11, MN 151 รายการ = 0 เช่นกัน) การใช้ `curStage`/`ckStatus` กับข้อมูลกลุ่มนี้จะได้ผลเหมือนเดิมทุกประการ (no-op)

## 6. Workflow การอัปเดตข้อมูล (Excel → Dashboard)

ผู้ใช้จะส่งไฟล์ Excel มาเป็นระยะ **โครงสร้างคอลัมน์เหมือนต้นฉบับทุกอย่าง** ขั้นตอนตอนอัปเดต:

1. อ่านไฟล์ Excel (ใช้ xlsx skill) แมปคอลัมน์ตามหัวข้อ 2
2. แทนที่ข้อมูลใน `AF` และ `MN` ด้วยชุดใหม่ทั้งหมด
3. **อัปเดตวันที่ 2 จุด:**
   - Header บนสุด: `"อัปเดต: DD-MM-YYYY(พ.ศ.) HH:MM น."`
   - `const UPD_REF_DATE=new Date(YYYY,M-1,D);` (เดือนใน JS Date เริ่มที่ 0)
4. **ห้ามแก้/ลบ** ฟังก์ชันในหัวข้อ 4 โดยไม่จำเป็น — โค้ด logic ควรทำงานได้ทันทีกับข้อมูลชุดใหม่ตราบใดที่โครงสร้างคอลัมน์เหมือนเดิม
5. ตรวจสอบก่อนส่งกลับทุกครั้ง:
   - JS syntax (`node -e "new Function(...)"` หรือเทียบเท่า)
   - จำลอง filter สำคัญด้วย Python/Node เทียบกับข้อมูลจริงชุดใหม่ (เช่น เช็คว่า pivot รวมคอลัมน์ = ยอดรวม, เช็คว่า curStage/ckStatus ยัง sync ถูกต้อง)

## 7. ประวัติการแก้ไข (สรุปสั้นๆ เรียงตามลำดับ)

1. ลบ filter "สถานะซ่อมถัดไป" (ov-next) ออกจากระบบทั้งหมด (เป็น dead code)
2. เพิ่ม "ไม่ดำเนินการ" เป็นตัวเลือกที่ 12 ใน filter สถานะซ่อมปัจจุบัน (`curStage`, `STAGES12`)
3. แก้ตาราง Pivot ให้รองรับ 12 คอลัมน์ ผลรวมตรงกับยอดรวมเสมอ
4. เพิ่ม `dCell()` ซ่อนคอลัมน์วันที่ (d01-d11) ที่ล้ำหน้าสถานะปัจจุบัน — เฉพาะตาราง Overview
5. เพิ่ม `ckStatus()` sync "เช็คสถานะซ่อมหลังสุด" ให้ตรงกับสถานะปัจจุบันเสมอเมื่อกำลังซ่อมอยู่ — เฉพาะตาราง Overview

ทุกจุดทดสอบกับข้อมูลจริง 1,023 รายการ (AF) ผ่านหมดแล้ว ณ วันที่เขียนเอกสารนี้
